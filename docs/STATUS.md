## 決定の記録(あとで「なぜこうした」を聞かれたときのため)

### フェードの秒数を3秒にした理由

`FadeOutSeconds = 3秒` / `SilentBeforeEnd = 0.8秒`(実質フェードがかかるのは残り3.8秒〜0.8秒の3秒間)。

**分かっている限界:** `GetDuration()`(動画ファイル全体の長さ)は分かっても、
**動画の中で実際に曲(音)が終わる位置**は分からない。YouTube動画は音声ファイルではなく映像作品なので、
曲が終わったあとエンドカードや無音区間が投稿者の匙加減でどれだけ付くかは動画によってバラバラ。

**それでも3秒という短さで実害が小さいと判断した理由:**
- 曲の後に長い無音・エンドカードがある動画(MV・歌ってみた系に多い)→ フェードは無音区間の中で起きる
  → 実害なし、ただ効果もない(空振り)
- 曲の後がほぼ余白の無い動画(Official Audio系)→ 本当の終わりの1〜2秒手前あたりからなめらかに下がる
  → ほぼ気づかれない。ぶった切りにはならない
- 唯一のリスクは「曲の最後の3〜4秒が、音量一定の伸ばした音(サビの一発・長い残響)で終わる曲」。
  ここは実際に下がって聞こえる可能性がある。頻度は低いと判断し、許容することにした。
- **もし他の人が `FadeOutSeconds` を大きく(10秒とか)伸ばすと、このリスクが顕在化しやすくなる。**
  Inspectorのツールチップで、伸ばしすぎるとOfficial Audio系の曲を削ってしまうリスクがあると
  まだ明記していない。追記の余地あり(未着手)。

### 重ねるクロスフェード(Phase8-5、実装済み・実機未確認)

ユーザーが本当にやりたかったのは、**前の曲が小さくなっている間に次の曲がもう鳴っていて、
同時に大きくなる**形。2026-09-27 に作り直した(前回 Phase7-5 は実機で機能しなかった)。

**仕組み**(`UdonCrossfadeCoordinator`、判断は `CrossfadeModel` の写し)
- 動画プレイヤー 2 つ(表・裏)。終わりの 28.8 秒前に次の曲を**裏で読むだけ**(鳴らさない)。
- 表が下がり始める所(残り 8.8 秒)で裏を鳴らし始める。表が終わったら裏を表に(**読み直さない**)。
- 音量の上げ下げは、実機で「使える」と確認済みの `UdonTrackFader` を 2 つ(Channel 0 / 1)使い回す。
  重ねるときは等パワーの曲線(`UdonMediaScreen.EqualPowerCurve`)で、真ん中で音が痩せない。
- 映像は混ぜない。面を 2 枚重ねて、音の大きいほうだけ表示する(混ぜるシェーダーは削除)。
- 重ねる長さ **8 秒**(`Crossfade` の Inspector の `FadeSeconds` で変えられる)。
  最初は 6 秒にしたが、実機で「一気に下がって一気に上がる」と感じたので 8 秒にした(2026-09-27)。45 秒未満の曲・長さの分からない曲は重ねない。

**失敗しても壊れない道**
- 裏の読み込みが間に合わない → 表が終わったら裏(読み込み中)を表にする → 重ねない方式と同じ聞こえ方。
- 裏の読み込みに失敗 → 裏の知らせは Session へ送らない。表はそのまま最後まで鳴り、今までの道で次へ。
- 手で別の曲を選んだ → 裏は止める。「次へ」で裏の曲を選んだ → 読み直さずに裏を表にする。
- 一時停止・バーを戻した・「この曲で止める」・あとで流す URL → 裏をやめる。
- 同期:おすすめで選ぶ次の曲は持ち主が 1 曲に 1 回だけ選び(`Session` の予約)、`_nextMedia` で配る。
  持ち主でない人は手元で音と映像だけ入れ替え、曲の切り替わりは同期で受け取る(読み直さない)。
- **Android(Quest)では既定で重ねない**(`AllowOnAndroid` が切れている)。動画プレイヤー 2 つ同時は重いため。
  切り替えは `#if UNITY_ANDROID`。U# の実行時コードで `#if` を使うのはここが初めてで、実機未確認。

**確かめ方**:`tools/typecheck/behaviour_sim/SimCrossfade.cs` が、偽の動画プレイヤーで時間を進めて
16 の流れ(上の失敗の道すべて・何曲も続ける・持ち主でない人)と Prefab の配線を確かめる。
直した所をわざと前回の形に戻すと失敗することも確認済み(裏の失敗で表が止まる・出口が同じ GameObject など)。

Phase7-5 が機能しなかった原因候補(コードを読んで見つけたもの。実機では未確認):
1. A・B 2 つの音の出口(AVPro のスピーカー)が同じ GameObject に付いていて、2 つめが使われず、入れ替え後に無音になる
2. 次の曲の準備を残り 10 秒で始めるが、混ぜ始めは読み込みが終わってから。読み込みが遅いと、混ぜる前に曲の終わりが来て打ち切られる
3. 読み込み完了のたびにスピーカー音量が人の決めた値に戻され、フェードが上書きされた(Phase8-3 で構造的に解消済み)
4. 同期は A 系統しか知らず、おすすめで次の曲を選ぶと人によって違う曲が選ばれる
5. 裏で読み込んだ次の曲が失敗すると、いま鳴っている曲まで止まる

作り直すときの懸念:
- Quest(Android)で動画プレイヤーを 2 つ同時に動かすのは重く、動くか分からない
- 動画の長さ = 曲の長さ、ではない(MV のエンドカード問題)。重ねる方式でも、無音区間に次の曲が重なるだけで害は小さい

**正確に直す方法(保留中):** 曲ごとに「フェード開始位置」をカタログにデータとして持たせる案がある。
下の「ブラウザ拡張機能」の構想に含まれる。YouTube動画をダウンロードして音声解析する案は
**却下**(YouTubeの利用規約に触れるため)。人間が聴きながらボタンを押して記録する方式を採用予定。

### プレイリストの設計

- 曲は**カタログの番号ではなくID**で覚える(カタログを作り直すと番号がずれるため)。
- 保存形式: `SMPPL1` ヘッダ + 行ごとに「名前 TAB ID TAB ID …」。壊れた行だけ捨てて残りは読む。
- お気に入り・履歴は今も**保存されない**(セッションだけ)。プレイリストだけPlayerDataに保存する。

### 対応言語の候補

英語・韓国語・繁体字中国語(簡体字より現実的、本土からのアクセス事情のため)・
ポルトガル語(ブラジル)・ロシア語・スペイン語・タイ語、あたりが候補。
確実な統計データがあるわけではなく一般論なので、実際にX投稿や類似ワールドのコミュニティの反応を見て
決めた方がいい。UIの組み込みフォント(`LegacyRuntime.ttf`)はOSフォントへのフォールバックなので、
PCなら大抵の言語がそのまま出るはずだが、**Questでの表示は未確認**(下のタスク#5と合わせて確認する)。
