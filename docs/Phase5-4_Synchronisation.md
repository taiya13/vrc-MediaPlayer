# Phase5-4 — 同期(みんなで同じものを見る)

**目的**: 複数人が同じ SmartMediaPlayer を共有できるようにすること。
β のゴールは **「全員が同じ動画を同じタイミングで見られる」** ところまでです。

---

## 0. どこに同期を置いたか

**`UdonPlayerSession` に `[UdonSynced]` を付ける**やり方もありますが、採りませんでした。

| やり方 | 何が起きるか |
| --- | --- |
| Session に直接付ける | 再生の判断と、ネットワークの都合が**同じクラスに混ざる** |
| **別の層を足す(採用)** | Session は今までどおり。同期を外せば 1 人用に戻る |

`UdonSyncCoordinator` という薄い層を 1 枚足しました。

```
          押す                        配る / 受け取る
UI ──→ UdonMediaController ──→ UdonSyncCoordinator ──→ (ネットワーク)
              │                        │
              │ 中継だけ                │ 写すだけ
              ▼                        ▼
       UdonPlayerSession  ←────────────┘
       (再生の判断はここだけ・無改造に近い)
              │
              ▼
       UdonVideoBackend   ← URL を知る唯一の場所
```

`UdonSyncCoordinator.Enabled` を false にすると、**Phase5-3 とまったく同じ 1 人用**に戻ります。

## 1. 同期したデータ一覧

**5 つだけ**です。すべて `UdonSyncCoordinator` にあります。

| 変数 | 型 | 何を表すか |
| --- | --- | --- |
| `_queue` | `int[]` | catalog index の並び。**先頭 = いま鳴っているもの** |
| `_playing` | `bool` | 再生中かどうか |
| `_baseServerTime` | `int` | 「この時刻のとき」を表すサーバー時刻(ms) |
| `_basePositionMs` | `int` | 「位置はここだった」を表す再生位置(ms) |
| `_revision` | `int` | 変わったことの目印 |

### 意図的に同期していないもの

| 同期しないもの | 理由 |
| --- | --- |
| **再生中のメディア** | `_queue[0]` がそれ。持つと二重管理になり、食い違う余地が生まれる |
| **再生位置そのもの** | 「いつ、どこだったか」から各自が計算できる。毎フレーム流す必要がない |
| **URL / タイトル / 長さ** | 全員が同じカタログを持っている。index だけで足りる |
| **選択中の項目**(`SelectedIndex`) | 手元の都合。人によって違ってよい |
| **音量 / ページ送り / パネルの開閉** | 同上。他人に押しつけない |

**この 5 つで再生位置まで揃うのが要点**です。

```
位置(いま) = 基準位置 + (再生中なら いまのサーバー時刻 − 基準サーバー時刻)
```

一時停止も「その時点の位置を基準に据えて、止める」だけで表せます。
seek も「動かした先を基準に据え直す」だけです。**専用の変数は要りません。**

計算の正典は `World/UdonModel/PlaybackClockModel.cs`(**EditMode 16 ケース**)。
`UdonSyncCoordinator.ExpectedPositionMs()` はその写しです。

> **サーバー時刻は `int` で、約 24.8 日で一周します。**
> 大小比較をすると「時間が巻き戻った」と誤解するので、**差だけを見ています**。
> 一周をまたぐケースもテストにあります(`TheClockSurvivesTheServerTimeWrappingAround`)。

## 2. Owner 権限の設計

所有権は **`SmartMediaPlayer/Sync` という専用の GameObject** に対して持ちます。
動画プレイヤーや画面と同居させると、操作のたびにそちらの所有権まで動いてしまうためです。

### 流れ

1. ボタンが押される → `UdonMediaController.Begin()`
2. `Sync.TakeControl()` が **操作してよいか**を判定
3. よければ `Networking.SetOwner()` で**その場で持ち主になる**
4. 操作を `UdonPlayerSession` へ中継
5. `Sync.Capture()` で状態を写して `RequestSerialization()`

**操作は必ず窓口(`UdonMediaController`)を通る**という Phase5-3 の設計のおかげで、
権限の判定は**この 1 か所だけ**で済んでいます。

### 3 つのモード(`Sync.AccessPolicy`)

| 値 | 名前 | 動き |
| --- | --- | --- |
| **0** | `AccessEveryone`(既定) | 誰でも操作できる。押した人が持ち主になる |
| 1 | `AccessMasterOnly` | インスタンスマスターだけ操作できる |
| 2 | `AccessOwnerOnly` | いまの持ち主だけ。`OnOwnershipRequest` で横取りを断る |

断られた操作は画面の Status 行に理由が出ます(「いまはマスターだけが操作できます。」)。
パネル右上には**いま誰が操作しているか**が常に出ます(`操作中: あなた` / `操作中: ○○さん`)。

### 動画の終了を誰が扱うか

`OnVideoEnd` は **全員の手元で別々に起きます**。全員が `Next()` すると、
人によって違うものが鳴り始めて同期が崩れます。

そこで `UdonPlayerSession` に `AutoAdvance` というフラグを 1 つだけ足し、
**持ち主だけ true** にしています。残りは同期で追いつきます。

`UdonPlayerSession` はこのフラグの意味(ネットワーク)を知りません。
**「自分で次へ進んでよいか」という 1 行だけ**を持っています。

## 3. 途中参加時の同期方法

**専用の仕組みは書いていません。** VRChat が入室したプレイヤーへ現在の同期値を
1 回送ってくれるので、そのまま `OnDeserialization()` が呼ばれます。

```
入室
 └→ OnDeserialization()
     ├ 1. Session.ApplySyncedState(queue, playing, current)   Queue と状態を写す
     ├ 2. 鳴らすものが違う → Backend.LoadAndPlay(current)      動画を読み込む
     ├ 3. 同じなら          → Backend.Play() / Pause()
     └ 4. Controller.NotifyChanged()                          パネルを書き直す
 └→ 1 秒後の見回りで位置を合わせる(CorrectDrift)
```

**位置合わせを 4 で即座にやらないのが要点**です。
動画は読み込みに数秒かかるので、その間の `SetTime` は効きません。
見回り(既定 1 秒ごと)が**ずれている限り何度でも合わせ直す**ので、
読み込みが終わった時点で自然に揃います。

`Backend.SetTime()` は読み込み中なら false を返して**何もしません**。

## 4. ネットワーク負荷を抑える工夫

| 工夫 | 効果 |
| --- | --- |
| **`BehaviourSyncMode.Manual`** | 変わったときだけ送る。毎フレーム流れない |
| **再生位置を流さない** | 「いつ、どこだったか」を 1 回配れば、あとは各自が計算する |
| **「いま鳴っているもの」を持たない** | `_queue[0]` がそれ。変数が 1 つ減る |
| **`int[]` は使っている長さだけ** | 固定長 64 ではなく、実際の件数ぶんだけ送る |
| **見回りは送信しない** | 位置のずれ直しは**受け取る側の手元だけ**で完結する |
| **同じ操作の二重発火を捨てる** | uGUI と「使う」の両方が反応しても送信は 1 回 |

### いつ通信が発生するか

- **操作したとき**(再生 / 停止 / 次へ / 行を押す / Queue を触る)…… 1 回
- **持ち主の動画が終わって次へ進んだとき** …… 1 回
- **持ち主が変わったとき** …… 所有権のみ

**何もしなければ通信はゼロ**です。1 曲 3 分なら 3 分に 1 回程度しか流れません。

### 1 回あたりの大きさ

`int[]`(Queue 5 件 = 20 byte)+ `bool` 1 + `int` × 3 = **おおむね 40 byte 未満**。

## 5. Prefab の変更点

### 増えたもの

```
SmartMediaPlayer
├── Screen
├── Player
├── Catalog
├── Session
├── Controller
├── Sync            ← 【新規】UdonSyncCoordinator(Manual sync)
└── WallPanel
```

**`Sync` が 1 つ増えただけ**です。パネルの中身・レイアウト・行の構造は変わりません。

### パネル側の変更

| 場所 | 変更 |
| --- | --- |
| パネル右上 | `SyncOwner`(Text)が 1 つ増えた。「操作中: ○○」を出す |

**それ以外の Prefab 構造は Phase5-3 と同一**です。すでに置いてあるパネルも
`Core` を挿し直す必要はありません(`Sync` は `Core` 経由で自動的に届きます)。

### Inspector で触るもの

| コンポーネント | 項目 | 既定 | 意味 |
| --- | --- | --- | --- |
| `UdonSyncCoordinator` | `Enabled` | true | false で 1 人用(Phase5-3 と同じ)に戻る |
| | `AccessPolicy` | 0 | **0=誰でも / 1=マスターだけ / 2=いまの持ち主だけ** |
| | `DriftTolerance` | 1.0 | 何秒ずれたら合わせ直すか |
| | `CheckInterval` | 1.0 | ずれを見に行く間隔(秒) |
| | `LogSync` | false | 同期の様子を Console に出す |

## 6. VRChat で確認すべきテスト項目

**2 人以上**で入る必要があります。`Build & Test` を 2 つ起動してください。

### A. 基本

1. 2 人が**同じ動画**を見ているか
2. 2 人の**再生位置がほぼ同じ**か(1 秒以内)
3. パネル右上に「操作中: ○○」が出ているか
4. A が「次へ」を押すと、**B の画面も切り替わる**か
5. A が「一時停止」すると、**B も止まる**か。再開すると **B も同じ位置から**再開するか
6. A が Library の行を押すと、**B もその曲になる**か
7. A が「＋」で Queue に足すと、**B の Queue にも増える**か
8. A が Queue の「×」を押すと、**B の Queue からも消える**か

### B. 操作者の入れ替わり

9. B が操作すると、**両方のパネルの「操作中」が B になる**か
10. 入れ替わった直後も、動画が飛んだり巻き戻ったりしないか
11. B が操作したあと A が操作すると、**また A に戻る**か

### C. 途中参加(ここが本題)

12. A が再生している状態で **B が後から入室**する
13. B に**同じ動画**が出るか
14. B の再生位置が **A とほぼ同じ**か(読み込みぶん数秒遅れてから揃えばOK)
15. B の Queue が **A と同じ並び**か
16. A が一時停止した状態で B が入室 → **B も止まった状態**で、同じ位置か

### D. 自動送り

17. 動画を最後まで再生 → **2 人とも同時に次へ進む**か
18. **1 人だけ先に進んでしまわない**か(← `AutoAdvance` が効いているかの確認)
19. URL が壊れているものを再生 → 2 人とも同じように次へ送られるか

### E. 権限モード

20. `Sync > Access Policy` を **1(マスターだけ)** にする
21. マスターでない人がボタンを押す → **「いまはマスターだけが操作できます。」**が出るか
22. マスターは操作できるか
23. `2(いまの持ち主だけ)` にして、持ち主以外が押したら断られるか

### F. 落ちないこと

24. 操作者が**退出**しても、残った人が操作を続けられるか
25. 全員が同時にボタンを連打しても、Udon エラーが出ないか
26. 30 分ほど放置しても位置がずれ続けないか

### G. 1 人用に戻せるか

27. `Sync > Enabled` を false → Phase5-3 と同じ動き(各自バラバラ)になるか

### よくある詰まり

| 症状 | 見るところ |
| --- | --- |
| 同期しない | `セットアップ > 操作 UI の配線を確認する` の「同期」の行 |
| 操作しても相手が変わらない | 窓口に `Sync` が挿さっているか(診断に出ます) |
| 位置だけ合わない | `Sync` の `Backend` が挿さっているか |
| 受信しても画面が古い | `Sync` の `Controller` が挿さっているか |

## 7. 今後改善できる同期精度や拡張点

### 同期精度

| 項目 | いまの状態 | 改善案 |
| --- | --- | --- |
| **位置合わせが `SetTime`** | ずれると一瞬飛ぶ | 小さいずれは**再生速度を 0.95〜1.05 倍**にして滑らかに寄せる |
| **読み込み待ちを見ていない** | 見回りで自然に揃うのを待つ | `OnVideoReady` を合図に 1 回だけ精密に合わせる |
| **全員が同じ瞬間に再生し始めない** | 各自の読み込み終わり次第 | 「この時刻に再生開始」を予告して**全員で待ち合わせる** |
| **`DriftTolerance` が固定** | 1 秒 | 端末の性能や回線に応じて自動調整 |
| **音ズレ** | 見ていない | AVPro の音声遅延を別に補正 |

### 機能の拡張

| 拡張 | いまの設計で足りるか |
| --- | --- |
| **シーク(好きな位置へ)** | ✅ `_basePositionMs` を書き換えて配るだけ。変数は増えない |
| **ループ / リピート** | `bool` を 1 つ足すだけ |
| **プレイリストの共有** | Queue と同じ形。`int[]` をもう 1 本 |
| **「リクエスト」機能**(非オーナーが曲を提案) | `SendCustomNetworkEvent` で持ち主へ送る。同期変数は増やさない |
| **投票スキップ** | 同上 |
| **視聴人数の表示** | `VRCPlayerApi.GetPlayerCount()`。同期不要 |

### Catalog Builder / サーバー連携が来たとき

**同期部分は変わりません。** 配っているのは catalog index だけで、
カタログの作り方も URL も `UdonSyncCoordinator` は知らないためです。

ただし 1 点だけ約束が要ります —— **全員が同じカタログを持っていること**。
index で指しているので、人によってカタログの中身が違うと別のものが再生されます。
サーバーからカタログを取ってくる形にするなら、
**カタログのバージョンも同期して、食い違いを検出する**のが安全です
(`_catalogVersion` を 1 つ足すだけで済みます)。
